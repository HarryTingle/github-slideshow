# /demos

Scripted walkthroughs. Two jobs, both important:

1. **Proof that a milestone is real.** A milestone is not done because the tests pass. It is done when someone can be walked through it end to end without the narrator apologising.
2. **The sales asset.** Internal adoption and, later, external design partners both start with a walkthrough. Writing it early forces the product to be explicable.

## Rules

- One file per demo: `NNNN-short-title.md`, using `_template-demo.md`
- Each demo names the specs it exercises and the milestone it proves
- **Real data, not lorem ipsum.** Use the reference engagement or a realistic anonymised engagement. A demo on invented numbers proves nothing and reads as a toy.
- Write the *narrative*, not just the clicks. What is the person trying to do, and what do they feel when it works?
- Record what broke. A demo that needed three attempts has told you where the product is weak — capture that in `REVIEW.md`.
- Note the runtime. If a demo of the core value takes more than ten minutes, the product is too slow to sell.

## The demo that matters most

**Demo 0002 — commercial flex.** Delivery plan already built, client asks for a different commercial shape, three defensible options produced live. If that demo lands, the product works. Everything else is supporting evidence.
